# ابزار ساخت کلید های مودیبان

این مخزن یک **برنامهٔ وب کاملاً سمت کاربر** است که جایگزین گردش‌کار OpenSSL برای
ساخت درخواست گواهی (CSR) و سپس فایل PKCS#12 (`.pfx`) می‌شود. راهنمای مرجع،
**«راهنمای ساخت CSR بر اساس پروفایل گواهی»** با شناسهٔ
`GICA.SW.User.CertProfilev1.0` نسخهٔ ۱.۰ مورخ ۱۴۰۴/۰۷/۲۵ است.

> **هیچ داده‌ای از دستگاه شما خارج نمی‌شود.** تمام عملیات رمزنگاری درون مرورگر
> انجام می‌شود؛ نه سروری وجود دارد، نه پایگاه داده‌ای، نه فراخوانی API و نه
> تحلیل‌گر آماری. کلید خصوصی هرگز از حافظهٔ مرورگر خارج نمی‌شود.

## شروع سریع

نیازمندی‌ها: **Node.js 22 یا بالاتر** (برای ساخت) و یک مرورگر به‌روز
(Chrome/Edge/Firefox) برای اجرا.

```bash
npm ci          # نصب دقیق نسخه‌ها بر اساس package-lock.json
npm run dev     # اجرای محلی روی http://localhost:5173
```

> ⚠️ **WebCrypto فقط روی `https://` یا `http://localhost` کار می‌کند.**
> اگر فایل `index.html` را مستقیم از روی دیسک باز کنید (`file://`)، مرورگر
> دسترسی به `crypto.subtle` را نمی‌دهد و برنامه کار نمی‌کند. برای استفادهٔ
> آفلاین از **نسخهٔ تک‌فایلی** (پایین) استفاده کنید یا فایل را از طریق یک
> وب‌سرور محلی سرو کنید.

### همهٔ بررسی‌ها به‌صورت یک‌جا

```bash
npm run verify   # typecheck + test + audit + build + build:single
```

## ساختار پروژه

```
src/
  core/                 ← منطق خالص، بدون هیچ وابستگی به React
    profiles.ts         ← تعریف داده‌محور پروفایل‌ها (فیلدها، ترتیب، زبان، CN)
    assumptions.ts      ← ثابت‌های مربوط به ابهام‌های راهنما
    dn.ts               ← ساخت Subject و config.txt، اعتبارسنجی فرم
    normalize.ts        ← یکسان‌سازی متن فارسی/عربی و ارقام
    validate.ts         ← الگوریتم‌های رقم کنترلی و اعتبارسنجی فیلدها
    keys.ts             ← تولید کلید (WebCrypto)، PKCS#8 (رمزدار/بی‌رمز)، PEM
    x509.ts             ← ساخت و راستی‌آزمایی PKCS#10 (CSR)
    pfx.ts              ← ساخت PKCS#12 (PFX) با node-forge
    noNetwork.ts        ← محافظ زمان اجرا: مسدودسازی همهٔ APIهای شبکه
  ui/                   ← لایهٔ رابط کاربری (React + Tailwind، راست‌به‌چپ)
    components/
      CsrForm.tsx       ← فرم تک‌صفحه‌ای ساخت CSR
      ui.tsx            ← اجزای مشترک (فیلد، وضعیت، دکمه، دانلود)
tests/                  ← تست‌های واحد + راستی‌آزمایی با OpenSSL واقعی
scripts/                ← اسکریپت audit و اسکریپت راستی‌آزمایی درون‌تطبیقی
```

لایهٔ `core` هیچ وابستگی‌ای به React ندارد و می‌تواند مستقلاً استفاده یا
آزموده شود؛ همین باعث می‌شود راستی‌آزمایی با OpenSSL روی هستهٔ واقعی برنامه
انجام شود، نه روی یک بازسازی تقریبی.

## پروفایل‌های گواهی

تعریف پروفایل‌ها در یک فایل داده‌محور (`src/core/profiles.ts`) قرار دارد؛ منطق
برنامه پراکنده نیست.

| # | پروفایل (تب رابط کاربری) | انواع | توضیح |
|---|--------------------------|-------|--------|
| ۱ | **شخص حقیقی** | فقط `Una` (مستقل) | پیوست ۱ راهنما |
| ۲ | **شخص حقوقی** | فقط `NGO` (غیردولتی) | پیوست ۲ راهنما |

پروفایل ۳ راهنما (دفتر ثبت‌نام) در هسته باقی است ولی طبق درخواست نهایی از
رابط کاربری حذف شده است.

الگوریتم ثابت و بدون گزینهٔ دیگر: **RSA-2048 / SHA-256 / RSASSA-PKCS1-v1_5**.

### ترتیب RDN (همان ترتیب OpenSSL)

موضوع گواهی دقیقاً مطابق نمونهٔ راهنما ساخته می‌شود:

```
CN, serialNumber, O, 1.OU, L, ST, C
```

(فیلدهای «نام واحد سازمانی ۱ تا ۳» طبق درخواست حذف شده‌اند؛ بنابراین فقط یک
`OU` با شمارهٔ `1.OU` تولید می‌شود — دقیقاً مثل نمونهٔ کاربردی راهنما.)

- مقادیر فارسی: `UTF8String`
- `C` و `serialNumber`: `PrintableString` (دقیقاً مثل خروجی OpenSSL)
- `E` (رایانامه): `IA5String`
- فیلدهای اختیاری خالی **کاملاً حذف** می‌شوند (هیچ RDN خالی ساخته نمی‌شود).

پیش‌نمایش زندهٔ «Subject» و معادل `config.txt` راهنما از رابط کاربری حذف شده
است؛ توابع ساخت آن‌ها در هسته (`src/core/dn.ts`) باقی است و در آزمون‌های
راستی‌آزمایی با OpenSSL استفاده می‌شود.

## گردش‌کار ساخت CSR

همه‌چیز **در یک صفحه** انجام می‌شود — بدون مرحلهٔ جداگانه و بدون پیمایش چندمرحله‌ای:

۱. **تب پروفایل** را انتخاب کنید: شخص حقیقی / شخص حقوقی
۲. **فرم** را پر کنید — فیلدها بر اساس پروفایل نمایش داده می‌شوند و خطاهای
   فارسی درست کنار هر فیلد (پس از تلاش برای ذخیره) نشان داده می‌شود.
۳. دکمهٔ **«تولید کلیدهای سازمان مودیبان»** را بزنید و در ناحیهٔ «وضعیت» مراحل
   را دنبال کنید
۴. سه فایل خروجی را **دریافت** یا **رونوشت** کنید:

| فایل | محتوا |
|------|--------|
| `CSR.txt` | درخواست گواهی (PKCS#10 PEM) — **همین را برای CA بفرستید** |
| `PrivateKey.key` | کلید خصوصی (PKCS#8 PEM، **بدون رمز**) — **محرمانه** |
| `PublicKey.pem` | کلید عمومی (SPKI PEM) |

> **کلید خصوصی رمز عبور ندارد** (دقیقاً مثل خروجی `openssl req -new -nodes` در
> راهنما). به همین دلیل فایل `PrivateKey.key` باید **محرمانه بماند و به هیچ‌کس
> داده نشود**.

سه خروجی در **سه باکس کنار هم** نمایش داده می‌شوند؛ دکمه‌های «دریافت» و
«رونوشت» بالای هر باکس هستند و محتوای فایل قابل انتخاب نیست (برای جلوگیری
از کپی تصادفی کلید خصوصی).

### چیدمان صفحه

- بالای صفحه دو تب «شخص حقیقی» و «شخص حقوقی» و زیر آن فرم در دو ستون.
- توضیح کوتاه هر فیلد **داخل خودِ فیلد** (placeholder) نوشته می‌شود.
- زیر فرم: ناحیهٔ «وضعیت» و سه باکس خروجی کنار هم.

پیش از نمایش نتایج، **خودارزیابی** انجام می‌شود: امضای CSR با کلید عمومی خودش
راستی‌آزمایی می‌شود و کلید خصوصی دوباره بارگذاری و با کلید عمومی مقایسه
می‌شود. اگر یکی از این دو شکست بخورد، هیچ خروجی نشان داده نمی‌شود.

### قواعد اعتبارسنجی

- **یکسان‌سازی متن**: `ي/ك/ى` عربی → `ی/ک` فارسی، حذف کشیدگی (تطویل)،
  فشرده‌سازی فاصله‌های تکراری، حذف نیم‌فاصله از ابتدا و انتهای متن
  (نیم‌فاصله درون متن حفظ می‌شود).
- **ارقام فارسی/عربی** در فیلدهای عددی به ارقام انگلیسی تبدیل می‌شوند.
- **فیلد انگلیسی**: فقط ASCII، **بدون فاصله**، و **با حرف اول بزرگ** — مثل
  `IranCenterForEcommerceDevelopment`. **فیلد فارسی**: حروف لاتین فقط هشدار
  است.
- **پسوندهای CN** (`[Sign]`, `[Stamp]`) و قالب «کد ملی» خودکار افزوده می‌شوند و
  کاربر نباید آن‌ها را تایپ کند.
- **کد ملی ۱۰ رقمی**: رقم کنترلی طبق الگوریتم استاندارد بررسی می‌شود؛
  نادرستیِ رقم کنترل **هشدار** است (می‌توان ادامه داد)، ولی طول یا
  غیرعددی بودن **خطا** است.
- **شناسهٔ ملی ۱۱ رقمی**: همان تفکیک (هشدار برای رقم کنترل، خطا برای قالب).
  مقدار `14000405500` از نمونهٔ راهنما معتبر تشخیص داده می‌شود.

## ساخت PFX (در رابط کاربری فعال نیست)

طبق درخواست نهایی، تب «ساخت PFX» از رابط کاربری حذف شد تا فرم ساده بماند.
اما **هستهٔ ساخت PFX** (`src/core/pfx.ts`) کامل و تست‌شده در مخزن باقی مانده
است:

- PKCS#12 با `node-forge` (PBES2 / AES-256-CBC) و حالت سازگاری قدیمی ۳DES
- بررسی تطابق کلید عمومی گواهی با کلید خصوصی (با WebCrypto)
- پذیرش گواهی PEM یا DER و زنجیرهٔ CA

برای فعال‌کردن دوباره کافی است یک تب در `src/ui/App.tsx` اضافه شود و کامپوننت
`PfxPanel` (که در `src/ui/components/` بود) برگردانده شود. آزمون‌های
`tests/pfx.spec.ts` و بخش «راستی‌آزمایی با OpenSSL» همچنان این قابلیت را
پوشش می‌دهند.

## آزمون‌ها

```bash
npm test           # همهٔ تست‌ها
npm run interop    # راستی‌آزمایی درون‌تطبیقی با OpenSSL (خروجی خوانا)
```

### تست‌های واحد

- یکسان‌سازی متن (عربی/فارسی، کشیدگی، فاصله، نیم‌فاصله، ارقام)
- هر دو الگوریتم رقم کنترلی (کد ملی ۱۰ رقمی و شناسهٔ ملی ۱۱ رقمی)
- ترتیب و کدگذاری RDN، و قالب‌های CN هر سه پروفایل
- ساخت/بازکردن PKCS#8 (رمزدار و بی‌رمز)، ساخت PFX مدرن و ۳DES، بررسی تطابق کلید

### آزمون سرتاسری با مرورگر واقعی (`tests/e2e.spec.ts`)

با `puppeteer-core` (بدون دانلود مرورگر) و یک Chrome/Edge نصب‌شده روی سیستم:

1. کل مسیر کاربر طی می‌شود: پر کردن فرم → تولید؛ سپس خروجی با
   `openssl req -verify` راستی‌آزمایی می‌شود.
2. تب «ساخت PFX»: ساخت `keystore.pfx` از گواهی و کلید هم‌خانواده.
3. حالت خطا: گواهی ناهمخوان با کلید → پیام خطای روشن.

اگر مرورگری روی سیستم نباشد، این آزمون‌ها خودکار رد (skip) می‌شوند.

### راستی‌آزمایی با OpenSSL واقعی (`tests/openssl-interop.spec.ts`)

1. تولید CSR با هستهٔ برنامه **و** با `openssl req -new -utf8 -config <config>`
   از همان ورودی، سپس مقایسهٔ **بایت‌به‌بایت** بخش Subject دو DER
   (ترتیب RDN و نوع رشته‌ها یکسان است).
2. `openssl req -in CSR.txt -noout -verify -text` موفق است و موضوع
   مورد انتظار (از جمله متن فارسی و صفت `2.5.4.97`) را نشان می‌دهد.
3. `openssl pkey -in PrivateKey.key` بدون رمز کار می‌کند و کلید عمومی استخراج‌شده از آن
   دقیقاً با فایل `PublicKey.pem` یکسان است.
4. PFX ساخته‌شده از یک گواهی خودامضا با `openssl pkcs12 -info` بررسی می‌شود.
5. تست «بدون شبکه»: هیچ درخواست شبکه‌ای انجام نمی‌شود و در خروجی ساخت
   هیچ نشانی بیرونی وجود ندارد (به‌جز شناسه‌های بی‌خطر فضای‌نام XML).

اگر `openssl` روی سیستم نصب نباشد، این تست‌ها به‌طور خودکار رد (skip)
می‌شوند؛ در CI روی لینوکس و ویندوز اجرا می‌شوند.

## ساخت و انتشار

### ۱) سایت ایستا (پیشنهادی)

```bash
npm run build      # خروجی: dist/
```

پوشهٔ `dist/` را روی هر وب‌سروری قرار دهید. فایل‌ها ایستا هستند و نیازی به
Node.js روی سرور نیست.

**پیکربندی nginx** (نمونهٔ کامل):

```nginx
server {
    listen 443 ssl;
    server_name csr.example.ir;

    root /var/www/gica-csr;
    index index.html;

    # ---- Content-Security-Policy ----
    # دقیقاً همان سیاستی که در برنامه اعمال می‌شود (به‌علاوهٔ frame-ancestors
    # که فقط در هدر قابل اعمال است)
    add_header Content-Security-Policy "default-src 'self'; connect-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; font-src 'self'; img-src 'self' data:" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "no-referrer" always;
    add_header Permissions-Policy "geolocation=(), camera=(), microphone=(), interest-cohort=()" always;
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header Cross-Origin-Opener-Policy "same-origin" always;
    add_header Cross-Origin-Resource-Policy "same-origin" always;

    # فقط فایل‌های ساخته‌شده (single page app)
    location / {
        try_files $uri $uri/ /index.html;
    }

    # فایل‌های دارای هش در نام، یک‌ساله کش می‌شوند
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }
}
```

**پیکربندی IIS** (در `web.config`):

```xml
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <system.webServer>
    <security>
      <requestFiltering>
        <hiddenSegments>
          <add segment="." />
        </hiddenSegments>
      </requestFiltering>
      <httpProtocol>
        <customHeaders>
          <remove name="X-Powered-By" />
          <add name="Content-Security-Policy" value="default-src 'self'; connect-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; font-src 'self'; img-src 'self' data:" />
          <add name="X-Content-Type-Options" value="nosniff" />
          <add name="Referrer-Policy" value="no-referrer" />
          <add name="Permissions-Policy" value="geolocation=(), camera=(), microphone=()" />
          <add name="Strict-Transport-Security" value="max-age=31536000" />
        </customHeaders>
      </httpProtocol>
    </security>
  </system.webServer>
</configuration>
```

> اگر سیاست امنیتی سازمان شما اجازهٔ استفاده از `unsafe-inline` در
> `style-src` را نمی‌دهد، آن را حذف کنید و در عوض هش SHA-256 بلوک‌های
> `<style>` را اضافه کنید؛ برنامه در ساخت تک‌فایلی به‌طور خودکار هش اسکریپت
> درون‌خطی را در CSP قرار می‌دهد.

### ۲) نسخهٔ تک‌فایلی آفلاین

```bash
npm run build:single   # خروجی: dist/index.html (یک فایل)
```

این فایل شامل HTML، CSS، JavaScript و **فونت وزیرمتن** است و هیچ ارتباطی با
شبکه ندارد؛ می‌توان آن را روی یک فلش یا در شبکهٔ داخلی توزیع کرد.

> باز کردن این فایل با `file://` در بعضی مرورگرها به‌دلیل محدودیت WebCrypto
> روی محیط ناامن کار نمی‌کند. در آن حالت فایل را با یک وب‌سرور محلی سرو کنید
> (مثلاً `npx serve dist`) یا از نسخهٔ سایت ایستا روی HTTPS استفاده کنید.

## نکات امنیتی

- **بدون سرور و بدون پایگاه داده.** هیچ API، CDN، Google Fonts یا ابزار
  تحلیلی وجود ندارد. فونت وزیرمتن به‌صورت محلی در `src/ui/fonts/` میزبانی
  می‌شود.
- **کلید و رمز فقط در حافظه.** هیچ کلید، رمز عبور یا CSR در
  `localStorage` / `sessionStorage` / `IndexedDB` / cookie / URL ذخیره
  نمی‌شود و هرگز در کنسول چاپ نمی‌شود. تنها چیزی که ذخیره می‌شود **ترجیح
  رنگ روشن/تاریک** است. با دکمهٔ «پاک‌سازی کامل» همهٔ ارجاع‌ها پاک می‌شوند و
  در صورت وجود کلیدِ ذخیره‌نشده، هشدار خروج از صفحه نمایش داده می‌شود.
- **محافظ شبکه در زمان اجرا** (`src/core/noNetwork.ts`): در ساخت نهایی،
  `fetch`، `XMLHttpRequest`، `WebSocket`، `EventSource` و `sendBeacon` مسدود
  می‌شوند؛ هر تلاش برای ارتباط شبکه خطا می‌دهد.
- **CSP سخت‌گیرانه** در `index.html` (به‌صورت `<meta>`) و در نمونهٔ سربرگ
  nginx/IIS بالا:
  `default-src 'self'; connect-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'`.
  اسکریپت درون‌خطی در نسخهٔ تک‌فایلی با **هش SHA-256** مجاز شده است
  (`'unsafe-inline'` برای اسکریپت هرگز استفاده نمی‌شود).
- **کلید خصوصی بدون رمز** (PKCS#8 با سربرگ `BEGIN PRIVATE KEY`) — همان خروجی
  `openssl req -new -nodes` که در نمونهٔ خودِ راهنما آمده است. به همین دلیل فایل
  `PrivateKey.key` باید **کاملاً محرمانه بماند**؛ هر کسی آن را داشته باشد، صاحب
  گواهی است.
- **امکان رمزگذاری** در هسته باقی است (PBES2 / PBKDF2-HMAC-SHA256 با
  ۳۱۰٬۰۰۰ تکرار / AES-256-CBC، نمک و IV تصادفی) و تب PFX فایل‌های رمزدار را
  هم می‌پذیرد.
- **نسخه‌های وابستگی‌ها دقیقاً سنجاق شده‌اند** و `package-lock.json` در
  مخزن ثبت شده است. `npm ci` همیشه همان نسخه‌ها را نصب می‌کند.
- **`npm audit` در CI اجرا می‌شود** (`npm run audit`).

### استثنای مستند در `npm audit`

`node-forge@1.4.0` (آخرین نسخهٔ منتشرشده) یک advisory بدون وصله دارد:
`GHSA-86w9-cpqp-85rv` — «RSA PKCS#1 v1.5 signature verification accepts extra
nested DigestAlgorithm elements».

این advisory فقط مسیر `forge.pki.rsa.verify` را تحت تأثیر قرار می‌دهد، یعنی
**راستی‌آزمایی امضای گواهی توسط خود node-forge**. این برنامه هیچ‌گاه از آن
مسیر استفاده نمی‌کند:

| کار | ابزار استفاده‌شده |
|-----|-------------------|
| راستی‌آزمایی امضای CSR | WebCrypto (`crypto.subtle.verify`) |
| راستی‌آزمایی امضای گواهی | WebCrypto |
| بررسی تطابق کلید و گواهی | WebCrypto (مقایسهٔ SPKI) |
| ساخت ظرف PKCS#12 | node-forge (فقط رمزنگاری و MAC) |

اسکریپت `scripts/audit-policy.mjs` در CI اجرا می‌شود و **هر آسیب‌پذیری
دیگری** را خطا می‌دهد؛ فقط همین یک advisory مجاز است.

## فرضیات قابل تأیید

راهنما در چند نقطه مبهم است. هر مورد با یک ثابت در
`src/core/assumptions.ts` پیاده‌سازی شده و در رابط کاربری هم نمایش داده
می‌شود. **پیش از استفادهٔ عملیاتی، این موارد را با مرجع صدور (CA) تأیید
کنید.**

1. **واحدهای سازمانی (OU).** نمونهٔ `config.txt` راهنما سه واحد با
   شماره‌های `3.OU/2.OU/1.OU` دارد، ولی جدول پیوست‌ها «نام سازمان» و سه واحد
   را جداگانه فهرست می‌کند.
   *تصمیم نهایی:* فیلدهای واحدهای ۱ تا ۳ حذف شده‌اند؛ فقط «نام سازمان» به‌عنوان
   یک OU با شمارهٔ `1.OU` تولید می‌شود (مانند نمونهٔ کاربردی راهنما).
   اگر سازمان شما چند واحد دارد، باید این فیلدها دوباره اضافه شوند.

2. **ترتیب RDN در پروفایل‌های ۱ و ۳.** راهنما فقط برای پروفایل ۲ ترتیب DN را
   نمونه می‌دهد.
   *پیش‌فرض:* همان الگوی نمونه؛ فیلدهای اضافه بلافاصله پس از
   `serialNumber` و به ترتیب جدول پیوست قرار می‌گیرند.
   - پروفایل ۱ (مستقل): `CN, serialNumber, E, SN, GN, O, L, ST, C`
   - پروفایل ۲ (غیردولتی): `CN, serialNumber, E, O, 1.OU, L, ST, C`

3. **قالب CN پروفایل ۳.** راهنما می‌نویسد «RaName. RA [National Code]» ولی
   نقطه‌گذاری دقیق مشخص نیست.
   *پیش‌فرض:* `{raName}. RA [{raNationalCode}]`

4. **ترتیب فیلدها.** تصاویر راهنما ترتیب متفاوتی از متن نمونه نشان می‌دهند.
   *پیش‌فرض:* متن نمونه (`config.txt`) ملاک است و همان ترتیب رعایت شده است.

5. **قالب نام انگلیسی در CN.** نمونهٔ راهنما CN را با فاصله نشان می‌دهد
   (`Iran Center for Ecommerce Development [Stamp]`)، ولی طبق تصمیم نهایی،
   فیلدهای انگلیسی باید **بدون فاصله و با حرف اول بزرگ** نوشته شوند؛ بنابراین
   خروجی به شکل `IranCenterForEcommerceDevelopment [Stamp]` خواهد بود.
   *تأیید لازم است:* آیا مرجع صدور نام فاصله‌دار را می‌پذیرد؟ اگر بله، کافی
   است قاعدهٔ `validateEn` در `src/core/validate.ts` به «فقط ASCII» برگردد.

نکتهٔ دیگر: صفت `2.5.4.97` (organizationIdentifier) طبق یادداشت راهنما با **OID**
ثبت می‌شود (نه نام)، که در خروجی `asn1parse` قابل مشاهده است.

## انحراف از کتابخانه‌های پیشنهادی

مشخصات فنی، `node-forge` را برای «کلید خصوصی رمزگذاری‌شدهٔ PKCS#8» و
«PKCS#12» پیشنهاد کرده بود. در این پیاده‌سازی:

| کار | کتابخانه | دلیل |
|-----|-----------|------|
| تولید کلید، امضا و **همهٔ راستی‌آزمایی‌ها** | WebCrypto | نیازمندی امنیتی |
| ساخت CSR (PKCS#10) | `pkijs` + `asn1js` | کنترل دقیق نوع رشته (PrintableString/UTF8String/IA5String) |
| **PKCS#8 رمزگذاری‌شده** | `pkijs` روی WebCrypto | `node-forge` الگوریتم PBKDF2 را به‌صورت خالص جاوااسکریپت پیاده می‌کند و **حدود ۲۵ برابر کندتر** است (اندازه‌گیری‌شده: ۳۱۰٬۰۰۰ تکرار → ۵٫۳ ثانیه در برابر ۰٫۱۸ ثانیه بومی). این اختلاف در رابط کاربری کاملاً محسوس است. |
| **PKCS#12 (PFX)** | `node-forge` | KDF مخصوص PKCS#12 در هیچ کتابخانهٔ دیگری به این شکل در دسترس نیست و مسیر «سازگاری قدیمی ۳DES» را همین کتابخانه به‌صورت استاندارد فراهم می‌کند (بدون نیاز به پیاده‌سازی دستی DES). |

هیچ ASN.1 دستی نوشته نشده است؛ ساختارها با کتابخانه‌های استاندارد
(asn1js / pkijs / node-forge) ساخته می‌شوند. تنها نقطهٔ استثنا، اصلاح کوچک
`RelativeDistinguishedNames.toSchema()` در `pkijs` است (که همهٔ صفت‌ها را در
یک `SET` می‌گذارد، در حالی که X.501 برای هر RDN یک `SET` می‌خواهد) — این
اصلاح در `src/core/x509.ts` با یک توضیح کامل آمده و خروجی آن **بایت‌به‌بایت**
با OpenSSL یکسان است.

### انحراف از مشخصات فنی (کلید خصوصی بدون رمز)

مشخصات فنی اولیه خواستار بود که فایل کلید خصوصی **رمزگذاری‌شده** (PKCS#8
رمزدار) و همراه آن رمز عبور باشد. طبق درخواست نهایی، این رفتار تغییر کرد:

- خروجی `PrivateKey.key` اکنون یک **PKCS#8 بی‌رمز** است (`BEGIN PRIVATE KEY`) —
  دقیقاً همان چیزی که `openssl req -new -nodes -keyout PrivateKey.key` می‌سازد و
  **همان چیزی که در نمونهٔ واقعی راهنما آمده است**.
- در نتیجه هیچ فیلد رمز عبوری در فرم ساخت CSR وجود ندارد.
- تب «ساخت PFX» همچنان **رمز خروجی PFX** را می‌پرسد (بدون آن، ویندوز فایل
  را باز نمی‌کند) و فایل‌های کلیدِ رمزدار را هم می‌پذیرد.

قابلیت رمزگذاری PKCS#8 در هسته (`encryptPkcs8`) باقی است و تست دارد.
